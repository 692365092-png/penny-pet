# 退出确认前保留恢复能力，释放阶段不再写盘

接续 `166e6f4`。检查同步退出等待时发现，问题不仅是阻塞耗时，还有关闭、确认和
释放的顺序错误。本节点先修复这些生命周期问题，不把尚未改造的同步等待称为已解决。

## 原有问题

1. 收到 `CloseAll` 最终快照后立即 `Host.BeginShutdown()`，之后才询问保存失败的
   用户是否取消。此时即使返回程序，便签宿主已经停止，既不能恢复刚关闭的窗口，也
   不能正常接受后续显示命令。Hosted membership 还保留着已关闭会话。
2. `OnFormClosed` 再次调用 `_notes.Save()` 和 `SaveLocation()`。选择独立紧急导出
   后，仍会重新等待可能阻塞的主写入器；选择放弃设置后，又会追加设置保存。最后的
   宠物位置也在保存确认之后才采集，该排队写入没有退出前完成的保证。
3. 外部 Close 在没有 hosted 便签时直接跳过退出确认；已有最终快照也被当作可以
   直接销毁的充分条件，尽管保存结果还没有得到处理。

## 改动

外部 Close 和菜单退出现在都进入 `BeginExitSequence`。只有已完成保存/导出/明确
放弃选择的告别阶段，才允许窗体销毁。宠物位置在保存确认前写入模型；关闭事件只负责
资源释放，不再写盘。用户确认退出后停止自动重试定时器，避免释放阶段重新启动保存。

`CloseAll` 的最终内容先按旧会话序号接收，再退休该批实际事实及全部会话标记。
退出与完整恢复共用这一接收函数，包含无可用最终快照的旧 session 的清理；不会把
已经关闭 HWND 的 watermark 留给重建窗口。临时缺屏意图仍保留在 placement runtime。

退出准备阶段只关闭便签窗口，保留宿主线程。保存失败后取消退出，会清除退出请求和
prepared 标记，并使用已有的显示/组恢复路径重建可见便签。真正的宿主 shutdown 由
Workspace 的释放负责。IME 未完成时的拒绝、完成后重试和保存故障的交互选择保留。
没有新建通用退出调度器、第二个保存队列或持久化 generation。

## 验证与剩余工作

595 次实际 MSTest 方法 / DataRow 调用通过，0 失败。新增三项真实 runtime 测试：
IME 尚未结束时取消保留活动会话；CloseAll 清除旧序号、焦点及删除标记后允许新会话；
prepared 后取消能够重新走一次完整退出。新增/更新源码边界检查覆盖外部关闭入口、
最终内容先接收后清理、宿主释放时机和禁止销毁阶段写盘。

Tests、Windows Core 的 92 个源码文件、SelfTests 的 5 个源码文件以警告视为错误
编译通过。测试调用使用此前记录的辅助 runner；Windows 的真实取消对话框、窗口
重建、告别动画和操作系统关机交互未在 Linux 运行，仍需 Windows 验收。

同步 `WaitForPendingSaves`、最终 `Save` 及紧急导出仍存在。后续异步化需要在模型
线程采集最终快照，以同一 writer 的回执驱动退出；还必须明确等待期间的新输入、
提醒、导入和重试的生命周期。只把现有循环放进 `Task.Run` 会把 live model 读取和
UI 对话框移到错误线程，不能作为合格的性能重构。
